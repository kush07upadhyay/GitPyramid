## **2\. Core Architectural Pillars & 3D UI Geometry Selection**

To ensure legal durability, sub-second load times, and 60 FPS rendering across desktop and mobile devices, GitPyramid is built on five foundational engineering pillars.

### **Pillar 1: Brand Identity & Trademark Compliance (gitpyramid.com)**

### **Pillar 2: The Curated Manifest & Upstream-PR Registry Architecture**

To stay lightweight, fast to clone, and compliant with open-source software licenses, the GitPyramid repository uses a **Curated Manifest & Upstream-PR Architecture** rather than storing third-party source code files inside the repo. This structure keeps the repository well under GitHub's 100 MiB file limit and 1 GB recommended repository size ceiling while avoiding license conflicts between permissive (MIT, BSD, Apache 2.0) and copyleft (GPLv2, GPLv3, AGPLv3) codebases.  
The gitpyramid monorepo consists of two core layers:

> 1. **The Foundation Brick (Platform Codebase):** Located in /apps/web, /packages/3d-engine, and /packages/ai-agent (licensed under MIT), this is the actual source code of gitpyramid.com. It occupies Brick \#0001 at the center of the Pyramid's base, enabling verified contributors to submit Pull Requests that improve the 3D interface, shaders, and AI search engine.  
> 2. **The Structured Brick Registry (/registry/bricks/\*.json):** Every curated open-source project in the Pyramid is represented by a schema-validated JSON manifest (\~2 KB per brick, licensed under CC0/MIT). Even at 50,000 repositories, the entire registry occupies only \~100 MB of text. Each manifest stores the repository's verified GitHub URL, website URL, category, problem statement solved, tech stack tags, license identifier, compatible companion bricks, and deterministic 3D grid coordinates. When community members fix bugs or improve documentation in an external open-source project, they submit the Pull Request *upstream* to that project's repository and record the merged PR link in GitPyramid to earn "Pyramid Builder" recognition.

### **Pillar 3: Selecting the Optimal 3D UI Shape — Solid Pyramid vs. Stepped-Ziggurat "Infinity Atrium"**

A central design decision for the 3D interface is selecting the geometric structure that best displays tens of thousands of variable-sized bricks across three visual states: **Solid Opaque** (mature, stable repositories), **Translucent** (actively building or rapidly evolving repositories), and **Wireframe Projection** (unclaimed slots showing the remaining capacity of the monument).  
Comparing a **Traditional Solid Pyramid** against a **Hollow-Core Stepped Ziggurat ("Infinity Atrium")** reveals why the Stepped Ziggurat is essential for both visual usability and GPU performance:

> 1. **Solving Internal Occlusion (100% Clickable Bricks vs. 88.5% Hidden Interior):** In a solid square pyramid of L layers where each layer l contains l^2 grid units, the total brick count follows the square pyramidal formula:N\_{\\text{solid}}(L) \= \\sum\_{l=1}^{L} l^2 \= \\frac{L(L+1)(2L+1)}{6} However, a user orbiting the exterior can only see the outer perimeter ring of each layer:N\_{\\text{surface}}(L) \= 1 \+ \\sum\_{l=2}^{L} 4(l-1) \= 2L(L-1) \+ 1 At L \= 50 layers, a solid pyramid contains 42,925 bricks, but only 4,901 bricks sit on the outer surface—meaning **88.5% of the repositories (38,024 bricks) would be permanently buried in the dark interior, invisible and unclickable**. By contrast, constructing the UI as a **Stepped Ziggurat with a Hollow "Infinity Atrium" Core** (using a 2-brick-thick stepped terrace shell t \= 2 plus concentric interior wings and floating dependency bridges inspired by *Demon Slayer*'s Infinity Castle) exposes 13,694 clickable bricks on a single 60-layer outer shell and scales to 50,000+ bricks across nested atrium rings where **100% of bricks have at least one exposed, clickable face**.  
> 2. **Discrete Octree Brick Volumes:** To ensure bricks pack together cleanly without overlapping polygons or floating gaps, brick volumes snap to **four discrete grid multiples** determined by their composite score: **1×1×1** (Modular Unit — 1× volume), **2×1×1** (Standard Ashlar — 2× volume), **2×2×1** (Structural Pillar — 4× volume), and **2×2×2** (Foundation Core — 8× volume).  
> 3. **3-Pass THREE.InstancedMesh Rendering (3 Draw Calls at 60 FPS):** In WebGL and Three.js, rendering thousands of individual THREE.Mesh objects creates severe CPU-to-GPU draw-call bottlenecks (Three.js performance targets recommend staying under 100 draw calls per frame). Furthermore, mixing transparent and opaque instances inside a single standard InstancedMesh causes depth-sorting occlusion bugs because instances render in fixed buffer order. GitPyramid solves both challenges by grouping all bricks into **three dedicated THREE.InstancedMesh passes**—rendering the entire monument in just **3 draw calls**:  
   * **Pass 1 — SolidBrickMesh (Stable/Completed Repos):** Standard MeshStandardMaterial with depthWrite \= true and per-instance colors updated via setColorAt() and instanceColor.needsUpdate \= true.  
   * **Pass 2 — TranslucentBrickMesh (Actively Building Repos):** Uses Three.js's built-in alphaHash \= true (dithered order-independent transparency) or @three.ez/instanced-mesh spatial sorting, delivering translucent visual differentiation without per-frame depth-sorting artifacts.  
   * **Pass 3 — EmptySlotWireframeMesh (Available Projection Slots):** Uses InstancedBufferGeometry wireframe segments to project the unbuilt silhouette of the Pyramid with zero alpha-blending overhead.

### **Pillar 4: The Logarithmic Pyramid Score (P\_{\\text{score}}) & Brick Sizing Engine**

Because GitHub metrics follow a steep power-law distribution (where flagship projects exceed 250,000 stars while vital specialized libraries may have 2,000 stars) and raw commit or branch counts can be skewed by bots or unmerged branches, GitPyramid evaluates repositories using a **100-point Logarithmic Pyramid Score (P\_{\\text{score}})**:  
P\_{\\text{score}} \= \\text{Popularity}\_{25} \+ \\text{Community}\_{25} \+ \\text{Stability}\_{25} \+ \\text{Impact}\_{25}  
Each pillar contributes up to 25 points using normalized GitHub GraphQL metrics and curator verification:

> 1. **Popularity (0–25 pts):** Calculated as 25 \\times \\left( 0.7 \\frac{\\log\_{10}(S \+ 1)}{5.5} \+ 0.3 \\frac{\\log\_{10}(F \+ 1)}{4.5} \\right), where S is stars and F is forks.  
> 2. **Community & Velocity (0–25 pts):** Calculated as 25 \\times \\left( 0.6 \\frac{\\log\_{10}(C \+ 1)}{3.5} \+ 0.4 \\frac{\\log\_{10}(M\_{1\\text{yr}} \+ 1)}{3.5} \\right), where C is human contributors (excluding bots) and M\_{1\\text{yr}} is commits over the past 12 months.  
> 3. **Stability & Maintenance Health (0–25 pts):** Calculated as 25 \\times \\left( 0.5 e^{-\\Delta t\_{\\text{push}} / 365} \+ 0.3 \\min\\left(1, \\frac{\\text{Age}\_{\\text{days}}}{730}\\right) \+ 0.2 R\_{\\text{issues}} \\right), where \\Delta t\_{\\text{push}} is days since the last commit, \\text{Age}\_{\\text{days}} measures repository maturity up to a 2-year cap, and R\_{\\text{issues}} is the closed-to-total issues ratio.  
> 4. **Ecosystem Uniqueness & Criticality (0–25 pts):** Calculated as 25 \\times U\_{\\text{impact}}, where U\_{\\text{impact}} \\in \[0, 1\] reflects domain criticality and uniqueness. If a newly submitted repository duplicates an existing use case without offering a distinct architectural trade-off (such as a different language runtime, edge compatibility, or memory footprint), it is linked as an "Alternative Option" inside the existing primary brick rather than cluttering the Pyramid with redundant bricks.

### **Pillar 5: Self-Sustaining Community Governance & Monument Epochs**

To scale gracefully to 50,000+ contributors while keeping curation quality high and avoiding low-effort pull request spam, GitPyramid uses three governance rules:

> 1. **The 4-for-1 Peer Review Protocol:** Modeled directly on the self-sustaining workflow of sindresorhus/awesome, every contributor who opens a Pull Request to add or update a brick must review at least **4 other open Pull Requests** (verifying repository activity, documentation quality, and schema accuracy). Fully AI-generated spam PRs or incomplete draft PRs are automatically rejected.  
> 2. **Automated GitHub Actions Gatekeeper:** Every PR modifying /registry/bricks/\<category\>/\<repo-slug\>.json triggers an automated CI workflow that queries the GitHub API to verify the repository is public, non-archived, actively maintained, and properly formatted before human review.  
> 3. **Monument Epochs (Multi-Spire Expansion):** Rather than permanently freezing the platform once the first Pyramid reaches 50,000 contributors or its 3-year milestone, each completed structure is enshrined as a **Monument Epoch** (e.g., *Pyramid I: The Foundation Era, 2026–2029*). Once Pyramid I is 100% solid, it remains permanently explorable while a connected spire opens inside the 3D Infinity Castle for next-generation technologies.

## **3\. Technical Architecture & Implementation Blueprint**

The system architecture decouples **static edge-cached 3D rendering**, **asynchronous GitHub metric ingestion**, and **cached AI stack synthesis**, enabling a solo founder to serve hundreds of thousands of users with near-zero server administration.

### **1\. Frontend & 3D Spatial Engine (The "Infinity Castle" UI)**

Built with **Next.js (Static Export) or Astro**, **Three.js**, **React Three Fiber (R3F)**, and **Tailwind CSS**, the frontend never queries a live SQL database just to render the 3D world. Instead, a scheduled build pipeline compiles all brick coordinates, discrete dimensions, RGB colors, and opacity states into a compact binary buffer (pyramid-manifest.bin) served directly from **Cloudflare Pages and R2**. Even at 50,000 bricks, the instance transformation matrices (64 bytes per brick) and color attributes (12 bytes per brick) require only **3.11 MB of GPU VRAM**—and under 600 KB over the wire when compressed.  
To make hovering and clicking across tens of thousands of bricks instantaneous on both desktop and mobile GPUs, the viewport integrates **three-mesh-bvh** (with raycaster.firstHitOnly \= true) and **@three.ez/instanced-mesh**, which provide Bounding Volume Hierarchy (BVH) spatial indexing and frustum culling. Rather than testing rays against every polygon sequentially, BVH tree traversal skips empty spatial branches and maintains 60 to 300 FPS. Brick visual attributes encode rich metadata at a glance:

> * **Color Hue (Domain Sector):** Blue (\#1A73E8) for Systems, Kernel & Infrastructure; Cyan (\#12B5CB) for Frontend, Web & UI/UX; Green (\#81C995) for Backend, APIs & Databases; Purple (\#C58AF9) for AI, LLMs & Agent Harnesses; Orange (\#FA903E) for DevOps, Security & Tooling.  
> * **Brick Opacity (Maturity State):** Solid Opaque (depthWrite \= true) for battle-tested repositories (P\_{\\text{score}} \\ge 55, active maintenance); Translucent (alphaHash \= true) for fast-rising new builds (\< 9 months old or actively under construction); Weathered Stone for dormant legacy projects (\> 365 days without a push); and Wireframe Outlines for open contributor slots.

### **2\. The Dual-Bucket GitHub Ingestion Pipeline**

To synchronize stars, forks, commit velocity, and issue health across tens of thousands of repositories without hitting rate limits, the background sync worker utilizes **GitHub's Two-Bucket Rate Limit Architecture**. GitHub provides two separate primary hourly budgets per authenticated token: **5,000 requests/hour on the REST API** (core bucket) and **5,000 points/hour on the GraphQL API** (graphql bucket), scaling up to 10,000–12,500 points/hour for GitHub Apps.

> * **GraphQL Batching (graphql bucket):** By batching 50 to 100 repositories per GraphQL query using node aliases, the worker refreshes core metrics for 50,000 repositories using \~1,000 GraphQL points per hour—staying well below the 5,000-point primary cap and the 2,000-point/minute secondary rate limit.  
> * **Conditional REST Fetching (core bucket):** README extractions and contributor verifications route through the separate REST bucket using HTTP ETag conditional requests (If-None-Match), where unchanged repositories return 304 Not Modified at zero quota cost.

### **3\. The "AI Stack Architect" RAG Search Engine**

The AI search bar uses a two-stage hybrid router to maximize speed and minimize token expenditure:

> * **Tier 1 — Instant Client-Side Filter (0 ms API latency, \$0 cost):** Lookups by brick ID (\#0042), repository name (react, fastapi), category, or visual filter ("show translucent AI agent bricks") execute directly against the in-memory Float32Array / JSON index in the browser, smoothly flying the 3D camera to the matching bricks.  
> * **Tier 2 — Edge RAG Stack Synthesis ("Build Anything" Mode):** When a user inputs an open-ended problem statement or project idea, the request routes to a **Cloudflare Worker**:  
  1. **Semantic Cache Check:** The Worker queries **Upstash Redis** (free tier: 250 MB data, 500,000 commands/month). Common stack requests hit the cache (60%–75% hit rate) and return in under 30 ms at \$0 LLM cost.  
  2. **Vector Embedding & Retrieval:** On a cache miss, the prompt is embedded via OpenAI's text-embedding-3-small (\$0.02 per 1M tokens, or \$0.0003 per 1,000 questions) or Cloudflare Workers AI's free tier (10,000 free Neurons/day). The vector queries **Supabase pgvector** (using 16-bit halfvec storage, which fits \~80,000 vectors in the 500 MB free tier) or **Upstash Vector** (free up to 10,000 queries/day) to retrieve the top 15 candidate bricks.  
  3. **LLM Synthesis & 3D Camera Choreography:** The 15 candidate manifests are evaluated by **Groq's Free Tier** (14,400 free requests/day on Llama 3.1 / Llama 4 Scout) or **Gemini 2.5 / 3.1 Flash-Lite** ($0.10–$0.25 per 1M input tokens). The LLM returns a structured JSON blueprint containing the optimal 4 to 6 compatible repositories, verifies that their licenses (e.g., MIT \+ Apache 2.0) can be legally combined, and instructs the 3D viewport to isolate those bricks and connect them with glowing dependency bridges.
